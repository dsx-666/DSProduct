# 电商销售数据洞察与品牌管理工作台

更新日期：2026-09-29。需求版本：v2.0。

保留 F1-F8 销售看板，增加三类身份、单品牌管理员权限、品牌筛选和人员管理。详见 [接口文档](接口文档.md)、[静态页面](index.html) 和 [前端说明](FRONTEND.md)。

**本次交付是接口目标契约和可交互静态前端。** 页面使用本地演示数据，不连接真实数据库。本次仅做数据库只读核查，没有执行 DDL、修改角色、创建账号或修改密码；后端实现需独立验收。

## 1. 用户与权限

| 身份 | user.role | 数据和功能 |
| --- | --- | --- |
| 普通用户 | NORMAL_USER | “我的订单”，只看本人订单及完整明细；禁止经营接口和人员管理 |
| 品牌管理员 | ADMIN | 只看所属品牌的全部经营数据；禁止其他品牌、人员管理、整单原金额与整单差额 |
| 超级管理员 | SUPER_ADMIN | 全部品牌、全部经营接口、完整订单与金额核对；查询人员、新增管理员、编辑姓名/角色/品牌/启停状态 |

**一个管理员只能负责一个品牌，一个品牌可以对应多个管理员。** 用户表上单个品牌字段即可表达，不需要多对多授权表。

`user.role` 是身份权限。`user.user_type` 的 NEW_USER/OLD_USER 是历史标签，不能作为角色；用户图仍按 signup_date 和固定业务日分类，不按角色或静态标签推导。

权限由后端登录会话确定。前端隐藏菜单、锁定品牌不能替代鉴权。每次请求重新校验账号状态、角色和所属品牌；停用、改角色、换品牌后旧权限不得继续有效。普通用户的 userId 也由会话取得，不接受客户端指定。

人员管理不提供删除账号、创建超级管理员、修改本人或其他超级管理员账号的入口，防止误操作导致失去管理权限。

## 2. 数据库核查

本次只读核查：MySQL 8.0.43；数据库 `DSProduct`；六张表为 user、product、order、order_item、event、review。

| 字段 | 当前结构 | 用途 |
| --- | --- | --- |
| user.user_id | BIGINT UNSIGNED，自增主键 | 用户和人员 ID |
| user.name | VARCHAR(100)，普通索引 | 展示姓名，不能作为可靠的唯一登录账号 |
| user.email | VARCHAR(255)，可空，唯一索引 | 使用现有邮箱登录；新增管理员必填 |

| user.signup_date | DATE，非空 | 注册日期 |
| product.brand | VARCHAR(100)，非空 | 真实品牌 |

## 3. 待审核的数据库补充

当前没有品牌归属、账号启停或并发编辑版本字段，建议在 user 增加：

| 字段 | 建议结构 | 规则 |

| lock_version | BIGINT UNSIGNED，默认0 | 人员修改乐观锁，版本冲突返回409 |

具体 [database-proposal.sql](database-proposal.sql) **仅供审核，尚未执行**，包含两个索引和角色/品牌约束，不新增人员、不提升角色、不改密码。product.brand 非唯一，不直接作为外键目标；后端在授权事务中验证品牌存在性。启用管理员必须已有品牌；缺少授权的异常历史账号按空范围处理，绝不回退为全库。

暂不新增 username 字段，复用唯一邮箱。缺邮箱账号先补全邮箱再登录。首次超级管理员需要另行确认目标账号和初始化方式，公开接口不能自行声明 SUPER_ADMIN。

后端应验证并保存密码哈希，不返回密码或哈希。本次只核查字段结构，不能据此认定现有密码实现已经符合要求。

## 4. 统计与品牌隔离

| 项目 | 规则 |
| --- | --- |
| 有效销售 | A3-A8 只统计 completed；A2/A9 可查看其他状态但不算销售 |
| 筛选关系 | 日期 AND 品类集合 AND 品牌集合；集合内 OR；品类、品牌、商品关键字必须命中同一明细 |
| 超级管理员品牌 | 不传 brand 表示全部品牌，支持多选；不传 category 表示全部品类 |
| 管理员品牌 | 不传 brand 仍只查所属品牌；传其他品牌整次请求403；页面显示锁定品牌 |
| 金额依据 | item_total 逐条按分归一后求和；有明细时优先使用，不回写原总额 |
| 管理员订单 | visibleAmount 为本品牌合计，matchedAmount 为进一步筛选合计；整单 amount、originalAmount、itemsTotalAmount、amountDifference、hasAmountDifference 均为 null |
| 跨品牌订单 | 在授权明细范围内按订单 ID 去重；摘要、缩略图、商品数和详情均不得带出其他品牌信息 |
| 无明细 | 仅超级管理员未选品类且未选品牌时纳入原金额回退，品类归入“未归类”；管理员排除 |
| 客单价 | 同一授权/筛选范围销售额除以去重已完成订单数，四舍五入至分；无订单为0 |
| 热销 | 合并范围内有销量商品数 N，按销量降序、金额降序、ID升序取 ceil(N×30%)；不能各品牌分别取再拼接 |
| TOP10 | amount 或 quantity，最多10个；热销标记与排行模式独立，评分仅供详情展示 |
| 用户分布 | 入选订单的购买用户按 user_id 去重；仅反映该范围购买用户，不包含其其他品牌消费 |
| 支付分布 | 按订单 ID 去重，未知支付方式保留并计入分母 |
| 差额 | 完整明细合计减原金额，绝对值大于0.01元为异常；整单核对仅超级管理员/订单本人可见 |
| 金额单位 | 人民币元，不提供币种选项 |

业务日固定 `2025-11-14`，默认近30天 `2025-10-16` 至 `2025-11-14`；快捷日期按业务日计算，起止日均计入，不随电脑日期变化。

新用户为相对业务日注册0-29天，满30天为老用户；注册日异常或关联缺失另列，新老占比以可分类购买用户为分母。不采用静态 user_type，不人为凑30%。历史下单早于注册不改变该分类规则，也不能据此推断真实客户生命周期。

前版全库快照发现587笔缺明细、2,300笔金额差异，已完成中分别113笔和460笔。这些不是任意品牌的异常数量，不能直接显示给品牌管理员。

全局筛选影响 A2-A8，查询后回到第一页；关键字、状态和分页只影响 A2。A9 不继承页面筛选，但始终执行身份授权。身份切换与退出清理旧数据和详情，阻止过期响应覆盖新身份。

人员管理独立于经营筛选；普通用户无经营导航，管理员无人员管理入口，后端必须同时拒绝这些越权调用。

原型默认进入超级管理员工作台，右上角可切换品牌管理员、无品牌账号及普通购买者；退出后可体验登录。所有账号、密码、订单和人员修改均在本地演示，刷新恢复初始状态，不能代替生产权限系统。

## 6. 接口目录

基础地址 `http://localhost:8080`，统一 code/message/data，成功 code=200。GET 用查询参数，POST/PATCH 用 JSON 请求体。

| 编号 | 方法与路径 | 权限 |
| --- | --- | --- |
| C1 | POST /api/auth/login | 邮箱密码登录 |
| C2 | GET /api/auth/me | 当前有效账号 |
| C3 | POST /api/auth/logout | 注销会话 |
| A1 | GET /api/categories | ADMIN/SUPER_ADMIN，可见品类 |
| A2 | GET /api/orders | ADMIN/SUPER_ADMIN，授权订单列表 |
| A3 | GET /api/orders/kpi | ADMIN/SUPER_ADMIN |
| A4 | GET /api/product/ranking | ADMIN/SUPER_ADMIN |
| A5 | GET /api/orders/stats | ADMIN/SUPER_ADMIN |
| A6 | GET /api/product/category-stats | ADMIN/SUPER_ADMIN |
| A7 | GET /api/user/customer-stats | ADMIN/SUPER_ADMIN |
| A8 | GET /api/orders/payment-stats | ADMIN/SUPER_ADMIN |
| A9 | GET /api/orders/{orderId} | 超级管理员全单，管理员本品牌 |
| A10 | GET /api/dashboard/meta | 经营初始化和权限范围 |
| A11 | GET /api/brands | 超级管理员全部品牌，管理员仅所属品牌 |
| P1 | GET /api/admin/users | 仅 SUPER_ADMIN |
| P2 | POST /api/admin/users | 仅 SUPER_ADMIN；新增 ADMIN |
| P3 | PATCH /api/admin/users/{userId} | 仅 SUPER_ADMIN；编辑普通用户或管理员 |
| U1 | GET /api/me/orders | 仅 NORMAL_USER，本人订单 |
| U2 | GET /api/me/orders/{orderId} | 仅 NORMAL_USER，本人订单详情 |

公共经营参数为 startTime/endTime/category/brand。品类、品牌、状态使用重复键，如 `brand=NeoTech&brand=Orion`；不接受逗号拼接、JSON字符串、brand[]。

filters.category、filters.brand、defaultFilters 中对应值都是数组；[] 表示不额外缩小授权范围，不能扩大角色权限。用户本人的 brand 是单个字符串或 null，不能混用数组。

400/20001 为参数错误；401 未登录/失效；403 无接口/品牌权限；404 订单不存在或不可见；409 并发修改/邮箱冲突；500 数据库/系统异常。空数据和失败分别展示。

## 7. 初始化与验收

1. C2 取得身份，401显示登录；普通用户走 U1/U2，管理员和超级管理员走经营接口。
2. 经营页并行读取 A1/A10/A11，再加载 A2-A8；A2默认page=1、num=20，A4传metric，A5传granularity，各接口只接收规定字段。
3. 同范围 KPI 金额等于趋势与完整品类金额之和，订单数等于趋势与支付订单数之和；TOP10、品类订单数不能按此简单相加。
4. 覆盖品牌与品类同明细匹配、重复值去重、清空选择、跨品牌裁剪、越权品牌403、无授权空范围、缺明细回退边界。
5. 普通用户更换订单 ID 不能查到他人订单；管理员和普通用户不能调用人员接口；导出遵循列表权限。
6. 校验同品牌多个管理员、禁止单账号多品牌、品牌变更立即生效、停用会话失效、保护本人/超级管理员、version冲突409。
7. 覆盖热销前30%、新老用户29/30天边界、分页、非法参数、空结果、失败重试与手机布局。

## 8. 实现边界

真实接入顺序：审核数据库补充及首次超级管理员初始化，完成会话与品牌权限，再对接经营、人员和本人订单接口。新增字段在批准执行前只存在于目标文档和演示模型。

真实运行必须后端查询 MySQL 返回 JSON；静态 JavaScript 和 CSV 不能作为生产鉴权。既有后端在日期、字段、金额、分页及路径上的差异仍需修复，本次未修改后端或数据库。

行为、评价、库存、预测、真实支付和多币种不在本版范围内；只描述已经实现和验证的能力。
