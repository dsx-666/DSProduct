# 电商销售数据洞察与品牌权限接口文档

版本：v2.0 目标契约；更新：2026-09-29。

基础地址：`http://localhost:8080`。JSON 编码：UTF-8。关联文档：[README](readme.md)、[静态前端](index.html)、[待审核数据库补充](database-proposal.sql)。

本版保留 A1-A10，新增 A11 品牌选项、C1-C3 身份会话、P1-P3 人员管理、U1-U2 本人订单。GET 参数放 URL，POST/PATCH 使用 JSON 请求体。以下为目标接口，不能据此认定现有 Java 后端已经完成；静态页面使用本地模拟服务。本次数据库操作全部为只读。

## 0. 公共约定

### 0.1 已确认的身份模型

| user.role | 中文 | 权限范围 |
| --- | --- | --- |
| NORMAL_USER | 普通用户 | 只能通过 U1/U2 查询本人订单；不能访问 A1-A11 和 P1-P3 |
| ADMIN | 品牌管理员 | A1-A11，只访问所属单个品牌；禁止人员管理 |
| SUPER_ADMIN | 超级管理员 | A1-A11 全局经营数据、P1-P3 人员管理 |

一个管理员只能负责一个品牌，一个品牌可分配给多个管理员。拟由 `user.managed_brand` 保存单个品牌，**该字段目前不存在，待审核后创建**。没有绑定品牌的管理员数据范围为空，不能解释为全部品牌。只有 SUPER_ADMIN 拥有全部品牌权限。

`user.role` 的真实枚举是 NORMAL_USER/ADMIN/SUPER_ADMIN；`user.user_type` 是 NEW_USER/OLD_USER 历史标签。不要新增 USER、BUYER 等不匹配数据库的角色值，不要把新老用户标签当权限。

权限来自服务端会话，不接受 role、userId、allowedBrands、scope 等客户端字段来声明身份。所有查询、详情、人员写操作均鉴权；停用、改角色和品牌变更后立即使用新权限，不能只在登录时缓存品牌且永不刷新。

### 0.2 响应、错误与会话

统一响应：

```json
{"code":200,"message":"响应成功","data":{}}
```

| 场景 | HTTP | code | 行为 |
| --- | ---: | ---: | --- |
| 成功，包括空集合 | 200 | 200 | data 按各接口定义 |
| 参数不合法 | 400 | 20001 | 日期、枚举、分页、未知参数、非法品牌格式 |
| 未登录、账号停用、会话失效 | 401 | 401 | 清除旧界面数据，进入登录页 |
| 角色无权访问、请求越权品牌 | 403 | 403 | 不降级为全库，不返回部分成功 |
| 订单不存在或不在可见范围 | 404 | 404 | 两种情况用相同文案，不泄露订单是否存在 |
| 人员不存在 | 404 | 404 | 仅在有人员接口权限后判断 |
| 邮箱冲突或人员版本冲突 | 409 | 409 | 不覆盖更新的人员信息 |
| 方法不支持 | 405 | 405 | GET 不得代替人员写操作 |
| 数据库失败 | 500 | 20003 | 不伪装成无数据 |
| 其他系统异常 | 500 | 500 | 不返回内部连接或堆栈信息 |

错误时 data=null，例如：

```json
{"code":403,"message":"无权访问所选品牌","data":null}
```

真实后端采用服务端会话 Cookie；生产使用 HttpOnly、Secure、SameSite，并限制允许的来源。登录成功更新会话标识，退出使会话失效。前端请求携带 credentials；POST/PATCH 需校验 Origin 和会话 CSRF token。C1/C2 返回 csrfToken，写请求使用 `X-CSRF-Token`。登录需校验来源并限制失败尝试。静态原型不建立真实 Cookie、CSRF 或服务器会话，不具备生产安全边界。

### 0.3 公共类型与默认值

- ID 是数据库正整数，不添加 O/P/U 前缀；当前数据在 JavaScript 安全整数范围内。未来超出安全整数范围需统一升级为字符串契约。
- 金额为人民币元的 number，逐条按分归一后再累加，前端显示两位小数；比例在0-1之间，最多六位小数。
- 日期格式 YYYY-MM-DD；订单时间 YYYY-MM-DD HH:mm:ss，时区 Asia/Shanghai；不带 UTC 的 Z。
- 固定业务日 businessDate=2025-11-14；默认30天2025-10-16至2025-11-14，包含起止日，不随电脑日期变化。
- 原配置 business.time=2025-11-15 是前版指出的待对齐差异，不代表本次已经改配置。
- 未知或无权访问的整单金额用 null，不能伪装成0。contentScope 明确区分权限裁剪与缺失数据。
- 全部经营图表只统计 completed。订单列表、详情可以展示其他真实状态，其金额不进入销售。
- 支付方式为银行卡支付、微信支付、支付宝支付；null显示“未知”。金额固定人民币，不增加币种筛选。

### 0.4 公共经营筛选 F

A2-A8 接收以下筛选。A1/A10/A11 不随筛选缩小选项；A9 不继承这些条件，但必须按身份裁剪。

| 参数 | 必选 | 类型 | 规则 |
| --- | --- | --- | --- |
| startTime | 否 | date | 含开始日；缺省取有效结束日前29天，按已知最早可选日截断 |
| endTime | 否 | date | 含结束日，缺省 businessDate |
| category | 否 | string重复键 | A1真实品类，多选 OR；省略表示不额外限制品类 |
| brand | 否 | string重复键 | A11真实品牌，多选 OR；省略表示不额外限制身份已有范围 |

1. 两日期都省略使用默认近30天；空日期视为省略。非法日期、开始晚于结束、超出业务日/允许范围返回400。快捷7/30/90天只传起止日期，不传 lastDays。
2. 品类与品牌取值去首尾空格、精确匹配、去重并排序。重复查询键示例：`category=Electronics&category=Clothing&brand=NeoTech&brand=Orion`。含空格和 & 的值用 URLSearchParams 编码。
3. 不能传空项、逗号拼接、JSON数组字符串、brand[]、brands、category[]、all、null。“全部”或清空选择时省略对应键。
4. SUPER_ADMIN 不传 brand 可以看全部品牌；ADMIN 不传 brand 仍只看 managed_brand。ADMIN 传非所属品牌，包括混入一个未授权值，整个请求403。普通用户访问经营接口403。
5. 同组内部 OR，日期/品类/品牌/状态之间 AND。品类和品牌必须命中**同一条明细**，不能用订单中的甲商品匹配品类、乙商品匹配品牌。
6. 先执行身份范围，再执行请求筛选，再做统计和分页。缺明细订单只有 SUPER_ADMIN 在 category 与 brand 都省略时可纳入。
7. 显式列出所有品类或所有品牌仍是明细筛选，会排除缺明细订单，不能代替省略参数。
8. A3-A8 不接受 statuses、keyWord、分页等额外条件；各接口只接受其参数表中的键，不得把整份页面状态直接序列化到所有接口。

A2-A8 公共返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| filters.startTime / endTime | date | 实际有效日期 |
| filters.category | string[] | 本次品类选择，[]表示不额外限制 |
| filters.brand | string[] | 本次品牌选择，[]表示不额外限制授权范围，不表示拥有全库权限 |
| filters.statuses | string[] | A2实际状态，A3-A8恒为completed |
| scope.mode | ALL / BRAND / OWN | 当前身份的数据范围类型 |
| scope.allowedBrands | string[] | ADMIN仅一个品牌或空数组；其他角色为[]，含义由mode决定 |
| scope.canViewFullOrder | boolean | SUPER_ADMIN可看全部完整订单，普通用户仅本人；ADMIN为false |
| scope.canManageUsers | boolean | 仅SUPER_ADMIN为true |

### 0.5 明细、金额与授权

先按身份取得可见明细：SUPER_ADMIN是完整订单，ADMIN仅所属品牌，NORMAL_USER仅本人订单完整明细。每条item_total归一到分精度再相加，历史价格用item_price/item_total，商品当前价仅作展示。

| 字段 | SUPER_ADMIN / 订单本人 | ADMIN |
| --- | --- | --- |
| contentScope | FULL / OWN | BRAND |
| amount | 完整明细优先的整单金额，无明细回退原额 | null |
| originalAmount | 原order.total_amount | null |
| itemsTotalAmount | 完整明细合计；无明细null | null |
| amountDifference | 明细合计减原额；无明细null | null |
| hasAmountDifference | 差额绝对值>0.01；无明细null | null，不能泄露其他品牌引起的异常 |
| visibleAmount | 与整单amount相同 | 本品牌可见明细合计 |
| visibleQuantity | 完整明细件数，无明细null | 本品牌可见件数 |
| totalQuantity | 完整明细件数，无明细null | null |
| amountSource | ITEM_SUM / ORDER_TOTAL | BRAND_ITEMS |
| items、摘要、商品数、缩略图 | 完整可见订单信息 | 仅本品牌，不含其他品牌名称、数量或缩略图 |
| matchedAmount（列表） | 可见范围内符合品类/品牌的金额，无筛选等于amount | 本品牌内进一步符合品类/品牌选择的金额 |

品牌管理员即使命中的订单碰巧只有一个品牌，也统一使用 BRAND 返回规则，不依靠推测开放整单字段。跨品牌同单在入选范围内按订单ID去重。金额异常阈值只控制提示，不改变明细优先金额。

A6跨品类订单会计入多个品类的订单数，各品类订单数不能相加作为KPI订单总数。A7按用户去重，A8按订单去重。TOP10不是全量商品销售额之和。

### 0.6 热销与新老用户

当前授权和筛选范围内累计销量大于0的不同商品数为N；热销取ceil(N×30%)，N=0时0。排序为销量降序、销售额降序、ID升序，不扩大并列数量。不分别按每个品类/品牌取30%后拼接。

TOP10支持amount/quantity，与热销集合独立。注册相对业务日0-29天为新用户，满30天为老用户；2025-10-16为新、2025-10-15为老。用户关联或日期异常单独统计，不能把异常占比混进新老饼图，因为分母不同。

user.role不影响历史订单是否计入销售。人员角色调整不能重写交易事实；购买用户去重使用order.user_id。历史下单早于注册不能据此推断生命周期，仍按约定完成销售统计。

## 2. 订单分页 A2

`GET /api/orders`；ADMIN/SUPER_ADMIN。

| 参数 | 必选 | 类型 | 规则 |
| --- | --- | --- | --- |
| F | 否 | 公共经营筛选 | 见0.4 |
| statuses | 否 | string重复键 | 默认completed；全部状态显式传五个真实值 |
| keyWord | 否 | string | 去首尾空格，最多100字符，订单ID精确匹配或商品名称包含匹配 |
| page | 是 | integer | 从1开始 |
| num | 是 | integer | 1-100；默认界面20 |

关键字中的%和_按普通字符处理，SQL必须参数绑定。商品名必须与品类、品牌同时命中同一可见明细。订单ID精确匹配仍需满足品牌、品类等条件。关键字只决定订单入选，matchedAmount累计该订单所有符合品类/品牌的明细，不只累计名称命中的商品。

先去重订单、再排序和分页；按createTime倒序、orderId倒序；offset=(page-1)×num。列表与total使用完全相同的权限和筛选条件。

| data字段 | 类型 | 含义 |
| --- | --- | --- |
| filters / scope | object | 见0.4 |
| keyWord | string/null | 有效关键字 |
| total / pageNum / pageSize | integer | 总订单数、页码、页大小 |
| orderList | object[] | 当前页，一行一单 |
| orderList[].orderId | integer | 数据库订单ID |
| amount / originalAmount / visibleAmount / matchedAmount | number/null | 见0.5；visibleAmount、matchedAmount始终为已知数字 |
| contentScope | FULL / BRAND | 明细与金额可见范围 |
| status / createTime | string | 原订单状态与北京时间 |
| userId / userName | integer / string或null | 购买用户；关联缺失仍保留交易 |
| payWay | string/null | 原支付方式 |
| productSummary | string | 可见商品按ID去重排序，最多展示两个名，超过追加“等N种商品” |
| productCount | integer | 可见不同商品数；缺明细0不等于真实销量0 |
| hasDetails | boolean | 是否存在可见明细 |
| hasAmountDifference | boolean/null | 见0.5 |

## 4. 商品 TOP10 A4

`GET /api/product/ranking`；接收F以及必填metric=amount或quantity。

销售额模式按金额降序、销量降序、ID升序；销量模式按销量降序、金额降序、ID升序。不支持rating或自定义limit。

| data字段 | 类型 | 含义 |
| --- | --- | --- |
| filters / scope | object | 公共返回 |
| metric / limit | string / integer | 实际指标；limit固定10 |
| soldProductCount / hotProductCount | integer | 全范围成交商品数和热销数，不是当前页条数 |
| rankList | object[] | 最多10项，不足不补虚假商品 |
| rankList[].rank | integer | 连续序号 |
| rankList[].product | object | productId、productName、category、categoryLabel、brand |
| salesAmount / salesVolume / isHot | number / integer / boolean | 本范围销售额、件数、是否热销 |

brand是单个真实品牌名，不是筛选数组。ADMIN结果不得出现其他品牌的名称、ID或金额。无商品时rankList=[]，两个商品计数0，limit仍为10。

样本全部品牌排序：商品1金额300、销量3、热销true；商品2金额100、销量2、false；商品3金额100、销量1、false。NeoTech管理员只返回商品1。

## 5. 销售趋势 A5

`GET /api/orders/stats`；接收F及必填granularity=day/week/month。

周以周一开始，月以1日开始；首尾不完整周期只统计请求范围，不扩大日期。无成交时间段补零。不支持year。

| data字段 | 类型 | 含义 |
| --- | --- | --- |
| filters / scope / granularity | object/object/string | 条件、权限、粒度 |
| dateList | date[] | 自然周期起点，升序 |
| periodStartList / periodEndList | date[] | 该周期实际纳入统计的首尾日期，按请求范围截断 |
| salesAmountList | number[] | 周期有效销售额 |
| orderCountList | integer[] | 周期去重订单数 |

五个数组长度一致。提示框显示实际periodStart/End，不只显示自然周期起点。全部品牌11-12至11-14金额[300,0,250]、订单[1,0,2]；NeoTech为[200,0,100]、[1,0,1]。按周dateList=[2025-11-10]，实际范围仍是11-12至11-14。

## 6. 品类销售 A6

`GET /api/product/category-stats`；只接收F。

| data字段 | 类型 | 含义 |

| filters / scope | object | 公共返回 |
| totalSalesAmount | number | 当前授权和筛选范围金额 |
| categoryList | object[] | 按金额降序 |
| category / categoryName | string或null / string | 真实品类及中文标签，缺明细分组null/未归类 |

## 12. 登录与会话 C1-C3

### C1 登录

`POST /api/auth/login`，JSON字段：email必填有效邮箱（最多255字符），password必填字符串（最多64字符）。不接收角色、品牌或用户ID。

```json
{"email":"neotech@example.test","password":"Demo123!"}
```

这是静态演示账号，不是真实数据库账号或密码。真实后端按现有唯一user.email定位账号，验证password哈希与account_status；姓名没有唯一约束，不作为登录键。缺邮箱账号需补齐后使用此登录方式。

成功设置会话Cookie并返回：

```json
{"code":200,"message":"响应成功","data":{"user":{"userId":9002,"email":"neotech@example.test","name":"陈予安","role":"ADMIN","roleLabel":"品牌管理员","brand":"NeoTech","status":"ACTIVE","version":1,"createdAt":"2025-01-01"},"scope":{"mode":"BRAND","allowedBrands":["NeoTech"],"canViewFullOrder":false,"canManageUsers":false},"csrfToken":"session-csrf-token"}}
```

brand是单个字符串或null，不是数组。密码错误、账号不存在或停用统一401，不区分暴露原因；响应不得出现password或passwordHash。

### C2 当前用户

`GET /api/auth/me`；无参数；有效会话返回与C1相同的data结构。role和brand每次由当前有效授权解析，不能信任浏览器保存值。无会话、账号停用或会话被撤销返回401。

### C3 退出

`POST /api/auth/logout`；空JSON对象，携带CSRF头。使当前会话失效，重复退出可幂等成功。

```json
{"code":200,"message":"响应成功","data":null}
```

退出或切换演示身份立即关闭详情和人员弹窗、清除表格、图表与导出缓存，取消请求或丢弃旧请求响应。

## 13. 人员管理 P1-P3

所有P接口仅SUPER_ADMIN。不得通过ADMIN身份读取人员列表，也不得通过构造POST/PATCH绕过按钮隐藏。所有修改在数据库事务中验证操作者当前权限、目标角色、品牌有效性和version。

人员对象：

| 字段 | 类型 | 映射/规则 |
| --- | --- | --- |
| userId | integer | user.user_id |
| email | string或null | user.email；新增管理员非空，唯一 |
| name | string | user.name，前端允许1-40字符 |
| role / roleLabel | string/string | NORMAL_USER普通用户、ADMIN品牌管理员、SUPER_ADMIN超级管理员 |
| brand | string/null | 拟新增user.managed_brand，最多一个品牌 |
| status | ACTIVE/DISABLED | 拟新增user.account_status |
| version | integer | 拟新增user.lock_version |
| createdAt | date | 现有signup_date，只精确到日期 |

不返回密码、哈希及无关个人资料。人员筛选不继承经营看板日期、品牌和品类。

### P1 查询人员

`GET /api/admin/users`。

| 参数 | 必选 | 说明 |
| --- | --- | --- |
| page / num | 是 | 页码>=1，每页1-100，界面默认1/10 |
| keyWord | 否 | 最多100字符，姓名或邮箱包含匹配，用户ID精确匹配 |
| role | 否 | 三个真实枚举之一，省略全部 |
| status | 否 | ACTIVE/DISABLED，省略全部 |

按SUPER_ADMIN优先、其余userId倒序稳定分页。返回data.userList人员数组、total、pageNum、pageSize。普通用户可查询和编辑，不需要把其作为管理员授权。

### P2 新增管理员

`POST /api/admin/users`。

| JSON字段 | 必选 | 规则 |
| --- | --- | --- |
| email | 是 | 有效唯一邮箱；重复409 |
| password | 是 | 初始密码8-64字符，后端哈希后存储；响应不回传 |
| name | 是 | 去首尾空格，1-40字符 |
| role | 是 | 只能ADMIN，禁止创建SUPER_ADMIN或普通购买者 |
| brand | 是 | 单个A11真实品牌；ACTIVE必须非空，DISABLED可以null |
| status | 是 | ACTIVE/DISABLED |

```json
{"email":"operator2@example.test","password":"Demo123!","name":"演示管理员","role":"ADMIN","brand":"NeoTech","status":"ACTIVE"}
```

同一品牌可以创建多个管理员，不能对managed_brand建唯一索引。传brand数组、空字符串或不存在品牌400。后端使用已有自增user_id；signup_date为实际创建日，不使用固定业务日伪造注册时间；user_type可置null，因为新老统计依赖signup_date。成功返回新人员对象，version以服务端实际值为准，不能假设必为1。

### P3 编辑人员

`PATCH /api/admin/users/{userId}`。

| JSON字段 | 必选 | 规则 |
| --- | --- | --- |
| version | 是 | 必须等于刚查询得到的版本，否则409 |
| name | 否 | 1-40字符 |
| role | 否 | 仅NORMAL_USER/ADMIN；不允许提升SUPER_ADMIN |
| brand | 否 | 字符串/null；普通用户必须null，启用管理员必须有效单品牌 |
| status | 否 | ACTIVE/DISABLED |

至少一个可修改字段。email、password、userId、createdAt不能借此修改；邮箱与密码变更流程不在本版。目标是本人或任何SUPER_ADMIN时403，不能停用/降级最后的超级管理员。接口不提供删除用户，以保留历史订单关联。

```json
{"version":1,"name":"演示管理员","role":"ADMIN","brand":"Orion","status":"ACTIVE"}
```

从ADMIN改为NORMAL_USER必须同时清空brand；提升普通用户为ADMIN且启用必须指定一个有效品牌。以`WHERE user_id=? AND lock_version=?`更新并加版本，受影响行为0则区分不存在/冲突。品牌、角色、状态修改成功后立即撤销旧会话或重新解析权限。停用不删除历史购买记录，也不改变历史经营统计。

## 14. 普通用户订单 U1-U2

### U1 我的订单

`GET /api/me/orders`，仅NORMAL_USER。

参数page/num必填，规则同A2；可选startTime/endTime、keyWord、statuses。默认从业务数据起始日到businessDate、全部五种状态；不接受category、brand、role、userId等参数。用户ID必须从会话读取，再附加 `order.user_id = 当前用户ID`。

返回结构复用A2，contentScope=OWN，scope.mode=OWN，visibleAmount=amount。商品摘要是本人订单完整商品；不能请求任意他人的订单列表。

### U2 我的订单详情

## 16. 兼容性与验收

v1.2路径保留A1-A10，无/api/order别名。参数仍用startTime/endTime/keyWord/statuses/page/num，新增brand重复键；不提供startDate/endDate/keyword/status/pageSize等别名。

本版明确替换旧规则：不再“所有接口都是GET”，不再“放行请求且不新增登录”，不再“管理员可见完整命中订单”。A9、A2完整字段含义按contentScope区分；SUPER_ADMIN保留原完整金额口径。filters和defaultFilters新增brand数组，统计响应新增scope。

必须验收：

1. 未登录401，普通用户调用经营接口403，ADMIN调用人员接口403；修改前端role/userId不扩大权限。
2. 超级管理员多品牌OR去重，品类和品牌同明细AND，管理员传其他品牌整次403；无归属或已不存在品牌空范围不变全局。
3. 跨品牌订单的列表、摘要、图片、数量、详情、CSV均只含本品牌。整单金额和差额的其他备用字段也不能泄露。
4. KPI金额=趋势金额合计=完整品类金额合计；KPI订单数=趋势订单合计=支付组订单合计。跨品牌/品类订单统一去重。
5. 未筛选的SUPER_ADMIN保留缺明细回退，具体品牌/品类或ADMIN排除；未知金额null、有明细0元不回退。
6. 热销前30%、TOP10不同排序、零销售、注册29/30天、异常用户单列、未知支付方式保留。
7. 普通用户只看本人；猜测他人订单ID返回与不存在相同404；停用或换品牌后旧会话立即失去原权限。
8. 新增管理员重复邮箱409；同品牌可多个管理员；单管理员不能多品牌；编辑需version，冲突409；超级管理员和本人账号受保护。
9. 快速切换筛选/身份时旧响应不能覆盖新结果；401清空旧数据，403/404与空结果分别展示；人员写入失败不能假装保存成功。
10. 只读核查与目标实现分开说明；待审核DDL未批准前不执行。前端演示通过不代表真实后端鉴权通过。
